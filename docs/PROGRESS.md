## Ключевые решения (кратко, подробно — в `docs/assumptions.md`)

- Синхронный SQLAlchemy 2.x + psycopg 3: проще для джуниоров, FastAPI запускает sync-эндпоинты в пуле потоков.
- Фоновая обработка — через `PipelineDispatcher` (сейчас пул потоков), позже можно заменить на очередь.
- Пайплайн — набор шагов «по статусу»: каждый шаг смотрит текущий статус и делает один переход.
  Поэтому обработку можно безопасно перезапустить (при старте бэкенд добирает «зависшие» заявки).
- Демо-история заявок для очереди сотрудника создаётся при seed теми же функциями, что и в API.

## Журнал этапов

### Этап 1 — каркас (готово)
- docker-compose: `db` (PostgreSQL 16.15), `mock-external`, `backend`; healthchecks, `restart: unless-stopped`, место под `frontend`.
- Имя compose-проекта задано явно (`name: credit-cabinet`): из кириллического имени папки Compose не может его вывести.
- Порт БД наружу не публикуется (чтобы не конфликтовать с локальным PostgreSQL у жюри).
- Lock-файлы `uv.lock` для backend и mock-external; образы закреплены по версиям.
- `/api/v1/health`, `/api/v1/ready` (проверяет БД и mock-external), JSON-логи с request id.

### Этап 2 — модели, миграции, seed, авторизация (готово)
- Модели всех сущностей ТЗ (`app/models/`), начальная миграция Alembic (autogenerate), UUID-ключи, номер заявки с 1001.
- Оптимистичная блокировка заявки через `version_id_col`.
- Бизнес-конфиги `backend/config/*.yaml` проверяются Pydantic-моделями при загрузке (`app/core/business_config.py`).
- Seed (`python -m app.seed`) идемпотентный, под `pg_advisory_lock`; продукты обновляются из YAML каждый старт.
- JWT (HS256), bcrypt, роли client/employee, rate limit на вход (in-memory). Проверено: 401, 429, повторный старт.

### Этап 3 — машина состояний (готово)
- `app/domain/state_machine.py`: таблица `TRANSITIONS` (из статусов, действие → статус, роли, предусловие, обязательный комментарий).
- `apply_transition()` — SELECT FOR UPDATE + проверки + запись `ApplicationEvent` в одной транзакции; 409 при недопустимом переходе.
- `available_actions()` возвращает кнопки с `enabled`/`disabled_reason` (например, «сначала загрузите документ»).
- `app/services/presenters.py` собирает ответ: `status_label`, `status_description`, `available_actions`, `timeline`, `info_request`, `offer`.
- Тексты — `config/labels.yaml`. Юнит-тесты таблицы переходов зелёные; через API проверяется на этапе 4.

### Этап 4 — клиентские эндпоинты (готово)
- `/company`, `/applications` (список, создание, просмотр, PATCH черновика с `version`), `/applications/{id}/actions/{action}`.
- `/products`, `/products/recommend` (правила и тексты — `products.yaml`), `/dictionaries/purposes`, `/dictionaries/document-kinds`, `/calculator`.
- Документы и договор (`/applications/{id}/documents`, `/contract`) написаны заранее — проверяются на этапе 8.
- Идемпотентность: повтор последнего действия тем же пользователем возвращает текущее состояние (200), а не 409.
- Проверено запросами: 409 при конфликте версий и недопустимом переходе, 404 на чужую заявку, 403 сотруднику в клиентском разделе.

### Этап 5 — mock-external и клиент интеграций (готово)
- `mock-external`: `/egrul/{inn}`, `/bki/report?inn=`; данные из `seed/external_mocks.json`, для неизвестного ИНН — детерминированная генерация.
- Режимы сбоя: `timeout`, `error` (500), `flaky` (каждый нечётный запрос — 503, видно ретраи).
- `app/integrations/external_client.py`: интерфейс + HTTP-реализация; таймаут, ретраи с экспоненциальной паузой, 4xx не повторяются,
  наружу исключения не летят — результат со статусом ok/error/timeout. Request id пробрасывается в мок.
- Юнит-тесты клиента на `httpx.MockTransport`; проверено и вживую из контейнера бэкенда.

### Этап 6 — скоринг, решение, предложение, пайплайн (готово)
- `domain/validation.py` (VALIDATION), `domain/scoring.py` (факторы → баллы → грейд), `domain/decision.py`
  (стоп-факторы → ошибки интеграций → нехватка данных → грейд → встречное предложение), `domain/payments.py` (аннуитет).
- `services/pipeline.py`: шаги по статусу, по одному переходу в транзакции; сбой шага → `technical_error` → MANUAL_REVIEW;
  при старте бэкенд возобновляет прерванные заявки (проверено перезапуском контейнера посреди обработки).
- Все 6 демо-учёток дают ожидаемый исход через API: good → OFFER_SENT (as_requested), medium → OFFER_SENT (counter_offer),
  border → MANUAL_REVIEW, bad → REJECTED, info → NEEDS_INFO → (выписка + provide_info) → OFFER_SENT, timeout → MANUAL_REVIEW.
- Цепочка accept_offer → sign → ISSUED, договор HTML сохраняется документом; загрузка файлов проверяет тип по сигнатуре.

### Этап 7 — бэкофис и статистика (готово)
- `/backoffice/applications` (фильтры status — несколько, product, grade; пагинация), карточка `/backoffice/applications/{id}`:
  компания, автор, проверки с кратким резюме, скоринг с вкладом факторов, итог авторешения, `suggested_offer`, история с payload.
- Действия сотрудника `approve` (можно поменять сумму/срок/ставку), `counter_offer`, `request_info`, `reject` — комментарий обязателен.
- `/backoffice/stats`: по статусам, доля автоодобрений, среднее время от отправки до решения.
- Демо-история для очереди (`seed/applications.json`, 8 заявок во всех ключевых статусах) создаётся при seed через сервисы и пайплайн.
- Найдена и исправлена гонка: `SELECT ... FOR UPDATE` в SQLAlchemy падал StaleDataError, если объект заявки в сессии устарел
  (пайплайн менял её в другом потоке). Теперь `lock_application` сначала блокирует строку, затем перечитывает заявку.

### Этап 8 — документы, подписание, выдача (готово)
- Загрузка: только в DRAFT/NEEDS_INFO, вид документа из `dictionaries.yaml`, расширения из env, проверка сигнатуры файла,
  лимит размера, пустые файлы отклоняются, имя файла очищается, на диске — случайное имя в папке заявки.
- Скачивание клиентом (только своей компании) и сотрудником; `Content-Disposition: attachment`, `nosniff`.
- `sign`: договор HTML по шаблону `config/contract_template.html` сохраняется документом «Кредитный договор»;
  `SIGNING → ISSUED` делает пайплайн (событие с суммой). Проект договора — `GET /applications/{id}/contract`.

### Этап 9 — лента подсказок (готово)
- `GET /feed` (только клиент): 17 подсказок в `seed/feed_items.json`, правила и тексты «почему показано» — `config/feed.yaml`.
- Условия: префикс ОКВЭД, тип компании, статус и продукт текущей заявки; все условия подсказки должны совпасть.
- Текущая заявка — последняя незавершённая, иначе последняя.

### Этап 12 — проверка глазами жюри (раунд 1)
Субагент-«жюри» поднял всё с нуля по README, прошёл сценарии 1–10 и чек-лист DoD: блокеров нет, все пункты DoD выполнены.
Найдено и исправлено:
- (важно) после `request_info` сотрудника ответ клиента автоматически решался пайплайном — клиент мог «поправить» анкету
  и обойти специалиста. Теперь решение возвращается к сотруднику (`returned_to_employee`), кроме стоп-факторов.
- (важно) эвристика идемпотентности отвечала 200 на повтор действия, даже когда процесс уже ушёл дальше
  (например, `submit` в NEEDS_INFO). Теперь повтор признаётся, только пока заявка в целевом статусе действия или в автообработке.
  Тест `test_repeated_action_is_idempotent` обновлён под уточнённое правило (поздний повтор → 409) — это изменение
  требований, а не подгонка: прежнее поведение было дефектом.
- 500 без `X-Request-ID` и без трейса: ошибка теперь ловится в `RequestIdMiddleware`; `page` ограничен 100 000 (было 500 на огромном числе).
- Сторож пайплайна: раз в минуту возобновляет застрявшие заявки (раньше — только при старте); чтение статуса — под try.
- Лимит документов на заявку (20); «or» в сообщениях валидации переведён; заголовок события проверок нейтральный.
- Swagger UI/ReDoc с закреплёнными версиями CDN; Postman: загрузка выписки без ручного выбора файла, пауза 20 с для таймаута.
- Документация: advisory lock только на seed (исправлена формулировка), ER-диаграмма дополнена колонками.
Тесты: 164 зелёных.

### Ревью интерфейса по чек-листу frontend-design (готово)
Прошёл все экраны по скриншотам. Искал признаки шаблонного интерфейса и тексты, непонятные предпринимателю без
банковского опыта. Цвета, шрифты, формы карточек и раскладку из Figma и `docs/design` не менял. Нумерацию шагов анкеты
и подбора оставил: там действительно последовательность. Что исправлено:
- бейджи статусов пишутся обычным регистром, а не капслоком (`theme.ts`);
- на экране входа логины демо-учёток показаны обычным мелким текстом, без моноширинного шрифта; описания сценариев
  переписаны простыми словами, без стрелок (`texts/demoAccounts.ts`);
- в мета-строках убран разделитель «·»: «1 500 000 ₽ на 24 мес., обновлена…», «Попыток: 1, ответ за 120 мс…»;
- в шапках заявок номер и продукт читаются как фраза: «Заявка № 1063: кредит на оборотные средства на 1 500 000 ₽»;
- на главной «Ваш следующий шаг» больше не предлагает «Редактировать» или «Отозвать заявку», только главное действие;
  вторая подпись пишется со строчной буквы («Принять предложение или отказаться от предложения»);
- в истории заявки у сотрудника убраны технические коды статусов (`scoring → decided`), осталось кто и когда;
- убран бейдж «Запрос от: Система» в блоке «Что нужно от вас»: клиенту он ничего не говорит;
- в блоке «Документы» больше нет противоречия «загрузите здесь» рядом с отдельной формой запроса: если банк просит
  документ, текст отправляет в блок «Что нужно от вас»;
- причина неактивной кнопки после двоеточия пишется со строчной буквы.
Тесты: интерфейс 12, бэкенд 183, все зелёные. Скриншоты в `docs/screenshots/` пересняты.

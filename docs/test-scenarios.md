# Сценарии проверки

Эти же сценарии автоматически проверяются e2e-тестами (`backend/tests/e2e/`). Ниже — как пройти их вручную.

## Подготовка

1. Запустите всё: `docker compose up --build` и дождитесь в логах `Uvicorn running on http://0.0.0.0:8000`
   (первый запуск — 2–4 минуты на сборку образов).
2. Откройте Swagger UI: http://localhost:8000/docs
3. Вход: `POST /api/v1/auth/login` → **Try it out** → тело `{"login": "client_good", "password": "client_good123"}` → **Execute**.
   Скопируйте `access_token`, нажмите **Authorize** (замок вверху справа), вставьте токен → **Authorize**.
   Чтобы сменить пользователя — **Authorize → Logout** и войдите заново под другим логином.

Есть и готовые коллекции запросов: Postman — [`docs/requests/credit-cabinet.postman_collection.json`](requests/credit-cabinet.postman_collection.json)
(токены и id сохраняются автоматически), VS Code REST Client — [`docs/requests/scenarios.http`](requests/scenarios.http).

### Стандартная анкета

Во всех сценариях клиентов используется **одна и та же анкета** — исход определяется данными компании
(госреестр, кредитная история, отрасль), а не тем, что ввёл клиент:

```json
{
  "product_code": "working_capital",
  "amount": 1500000,
  "term_months": 24,
  "purpose_code": "working_capital",
  "monthly_revenue": 800000,
  "monthly_expenses": 550000,
  "current_loan_payments": 0
}
```

### Как пройти один сценарий

1. Войти под клиентом (см. выше).
2. `POST /api/v1/applications` со стандартной анкетой → ответ `201`, `status: DRAFT`, `status_label: "Черновик"`.
   Скопируйте `id` заявки.
3. `POST /api/v1/applications/{id}/actions/submit` (тело можно не передавать) → `status: SUBMITTED`.
4. Несколько раз вызовите `GET /api/v1/applications/{id}`: статус меняется
   «Проверяем данные» → «Запрашиваем сведения» → «Оцениваем заявку» → итог (примерно за 5–10 секунд).
5. Смотрите в ответе: `status_label`, `status_description`, `available_actions` (какие кнопки показать),
   `timeline` (история с комментариями), `offer` (предложение), `info_request` (что донести).

## 1. `client_good` — автоодобрение и выдача

| | |
|---|---|
| Логин / пароль | `client_good` / `client_good123` |
| Компания | ООО «Северный ветер», 9 лет на рынке, рейтинг БКИ 790, без просрочек |
| Ожидаемый итог | `OFFER_SENT`, предложение `as_requested` |

Шаги и ожидаемые результаты:
1. Создать заявку и отправить (см. «Как пройти один сценарий»).
2. Итог: `status: OFFER_SENT`, «Есть предложение». `offer.offer_type: as_requested`, `offer.amount: 1500000`,
   `term_months: 24`, `rate: 17.5`, `monthly_payment: 74524.27`. В `timeline` последнее событие — «Банк одобрил заявку».
   `available_actions`: «Принять предложение», «Отказаться от предложения».
3. `GET /api/v1/applications/{id}/contract` — проект договора (HTML).
4. `POST .../actions/accept_offer` → `OFFER_ACCEPTED`. Доступно «Подписать договор».
5. `POST .../actions/sign` → `SIGNING`, через 1–2 секунды `GET` показывает `ISSUED` «Кредит выдан»,
   в истории «Деньги перечислены: на расчётный счёт компании перечислено 1 500 000 ₽ (имитация выдачи)».
6. `GET .../documents` — подписанный договор (`kind: contract`), скачивается по `download_url`.
7. Повторный `POST .../actions/sign` возвращает 200 и текущее состояние — дублей в истории нет (идемпотентность).

## 2. `client_medium` — встречное предложение

| | |
|---|---|
| Логин / пароль | `client_medium` / `client_medium123` |
| Компания | ООО «Пекарня Каравай»: уже платит 330 000 ₽/мес. по двум кредитам (данные БКИ), рейтинг 680 |
| Ожидаемый итог | `OFFER_SENT`, предложение `counter_offer` |

Итог: `offer.offer_type: counter_offer`, `offer_type_label: "На изменённых условиях"`, `amount: 1050000`,
`term_months: 24`, `rate: 21.5`. Комментарий в истории объясняет почему: «по результатам оценки можем предложить до 70%
от запрошенной суммы; платежи по кредитам заняли бы 51% выручки при допустимых 50%. Предлагаем: 1 050 000 ₽ на 24 мес. под 21,5% годовых.»

Дальше можно `decline_offer` (тело `{"comment": "Нужна вся сумма"}`) → `CLIENT_DECLINED`, или принять и подписать.

## 3. `client_border` — ручное рассмотрение сотрудником

| | |
|---|---|
| Логин / пароль | `client_border` / `client_border123`, затем `employee` / `employee123` |
| Компания | ИП Сидоров: бизнесу меньше 2 лет, стройка (повышенный риск), просрочки до 45 дней в истории, рейтинг 560 |
| Ожидаемый итог | `MANUAL_REVIEW` → решение сотрудника |

1. Клиент создаёт и отправляет заявку → `MANUAL_REVIEW` «На рассмотрении у специалиста».
   Комментарий: «Пограничная оценка заявки, нужна проверка специалистом». Клиенту доступно только «Отозвать заявку».
2. Войти как `employee`. `GET /api/v1/backoffice/applications?status=MANUAL_REVIEW` — заявка в очереди, грейд `D`.
3. `GET /api/v1/backoffice/applications/{id}` — карточка: `company`, `checks` (ЕГРЮЛ и БКИ с кратким `summary`),
   `scoring` (балл 45 из 100, грейд D и вклад каждого из 6 факторов с объяснением), `decision`, `suggested_offer`
   (1 500 000 ₽ на 24 мес. под 23,5%), `events` с техническими деталями.
4. `POST /api/v1/backoffice/applications/{id}/actions/approve` с телом
   `{"comment": "Одобряем на меньшую сумму", "amount": 1200000, "term_months": 30}` → `OFFER_SENT`, предложение `counter_offer`.
   Без комментария — 422; сумма вне лимита продукта — 400.
5. Клиент видит предложение 1 200 000 ₽ и комментарий специалиста в истории; может принять и подписать → `ISSUED`.

Другие решения сотрудника (на новой заявке того же клиента):
- `reject` с `{"comment": "Высокая нагрузка и просрочки в истории"}` → `REJECTED`, клиент видит причину.
- `request_info` с `{"comment": "Пришлите отчётность", "requested_documents": ["financial_report"], "requested_fields": ["monthly_revenue"]}`
  → `NEEDS_INFO`, клиент видит, что именно нужно.
- `counter_offer` с `{"comment": "...", "amount": 1000000, "term_months": 36}`.

## 4. `client_bad` — отказ

| | |
|---|---|
| Логин / пароль | `client_bad` / `client_bad123` |
| Компания | ООО «Ромашка-Строй»: в процессе ликвидации (ЕГРЮЛ), текущая просрочка 65 дней (БКИ) |
| Ожидаемый итог | `REJECTED` |

Итог: «Отказ», `available_actions: []`, `is_final: true`. В истории: «Банк отказал в кредите. Причина: по данным
госреестра компания имеет статус «В процессе ликвидации»; есть непогашенная просрочка по кредитам (65 дн.).»

## 5. `client_info` — запрос уточнений

| | |
|---|---|
| Логин / пароль | `client_info` / `client_info123` |
| Компания | ИП Петрова, салон красоты: нет годовой выручки по отчётности |
| Ожидаемый итог | `NEEDS_INFO` → после выписки `OFFER_SENT` |

1. Создать и отправить заявку → `NEEDS_INFO` «Нужны уточнения».
   `info_request.comment`: «У нас нет данных о выручке вашей компании по отчётности. Загрузите, пожалуйста, выписку...»,
   `info_request.documents`: `[{"kind": "bank_statement", "label": "Выписка по расчётному счёту за 6 месяцев", "uploaded": false}]`.
   В `available_actions` кнопка «Отправить уточнения» с `enabled: false` и `disabled_reason` «Сначала загрузите документы...».
2. `POST .../actions/provide_info` сейчас → 409 с тем же объяснением.
3. `POST /api/v1/applications/{id}/documents` (multipart): `kind = bank_statement`, `file` — любой PDF → 201.
   В заявке `uploaded: true`, кнопка стала активной.
4. `POST .../actions/provide_info` с `{"comment": "Выписку загрузила"}` → заявка снова проходит проверки → `OFFER_SENT`
   (1 500 000 ₽ на 24 мес. под 17,5%).

## 6. `client_timeout` — сбой БКИ

| | |
|---|---|
| Логин / пароль | `client_timeout` / `client_timeout123` |
| Компания | ООО «ТехноСервис»: бюро кредитных историй не отвечает (мок «зависает» на 10 секунд) |
| Ожидаемый итог | `MANUAL_REVIEW` |

1. Создать и отправить заявку. Статус «Запрашиваем сведения» держится ~8 секунд: бэкенд делает 3 попытки
   по 2 секунды с паузами 0,5 и 1 секунда.
2. Итог: `MANUAL_REVIEW`. В истории: «Не удалось получить данные: Бюро кредитных историй. Заявку проверит специалист.»
3. Сотрудник в карточке видит проверку БКИ со статусом `timeout` («Нет ответа»), `attempts: 3`, ЕГРЮЛ — `ok`;
   скоринг посчитан по доступным данным, причина решения — `integration_error`. Дальше — любое решение сотрудника.

## 7. Неполная анкета → уточнения → предложение

1. Под `client_good` создать заявку без выручки и с суммой вне лимита: стандартная анкета, но `"monthly_revenue": null, "amount": 100`.
2. Отправить → `NEEDS_INFO`. `info_request.fields`: «Выручка в месяц» и «Сумма кредита» с объяснениями,
   комментарий в истории перечисляет, что исправить.
3. `PATCH /api/v1/applications/{id}` с `{"monthly_revenue": 800000, "amount": 1500000}` → 200.
4. `POST .../actions/provide_info` → `OFFER_SENT`.

## 8. Рабочее место сотрудника

Под `employee`:
- `GET /api/v1/backoffice/applications` — очередь: уже есть демо-заявки фоновых компаний во всех ключевых статусах
  (на рассмотрении, с предложением, выданные, отказ, черновик, запрос уточнений). Фильтры: `status` (можно несколько),
  `product`, `grade`; пагинация `page`, `page_size`.
- `GET /api/v1/backoffice/stats` — заявки по статусам, доля автоодобрений, среднее время от отправки до решения.

## 9. Безопасность и надёжность

| Проверка | Как | Ожидаемо |
|---|---|---|
| Чужая заявка | Под `client_bad` открыть `GET /applications/{id}` заявки `client_good` | 404 «Заявка не найдена» |
| Разделение ролей | Клиент → `GET /backoffice/applications`; сотрудник → `GET /applications` | 403 |
| Без токена | Любой защищённый эндпоинт без Authorize | 401 «Нужно войти в систему» |
| Недопустимый переход | Черновик → `actions/accept_offer` | 409 «Действие «Принять предложение» сейчас недоступно: заявка в статусе «Черновик».» |
| Конфликт версий | Два `PATCH` с одной и той же `version` | второй — 409 `version_conflict` |
| Идемпотентность | Дважды `actions/submit` или `actions/accept_offer` | оба 200, в истории одно событие |
| Подбор пароля | 6 раз неверный пароль одного логина | с 6-й попытки 429 |
| Загрузка файла | `.exe`, «PDF» с чужим содержимым, файл > 10 МБ | 400 с понятным сообщением |
| Request id | Любой ответ | заголовок `X-Request-ID`; тот же id в логах `docker compose logs backend` |
| Перезапуск во время обработки | Отправить заявку `client_timeout` и сразу `docker compose restart backend` | после старта заявка дообрабатывается (в логах «Возобновлена обработка заявок») |

## 10. Справочники, подбор продукта, калькулятор, лента

Без входа:
- `GET /api/v1/products` — 4 продукта с описанием «для чего подходит» и `rate_text` («от 17,5% годовых»).
- `GET /api/v1/dictionaries/purposes`, `GET /api/v1/dictionaries/document-kinds`.
- `GET /api/v1/calculator?product=working_capital&amount=1500000&term=24` → платёж 74 524,27 ₽, переплата, пояснение.
- `POST /api/v1/products/recommend` с `{"purpose_code": "equipment", "amount": 2000000, "term_months": 36, "urgency": "month", "has_collateral": true}`
  → первым «Инвестиционный кредит» (`suitable: true`) с причинами; у неподходящих — `warnings`.

Под клиентом:
- `GET /api/v1/feed` — лента подсказок с объяснением `reason`. У `client_info` (ИП, салон красоты) — подсказки «Для ИП»
  и для её отрасли; у клиента с заявкой в `NEEDS_INFO` — подсказка, как быстро ответить на запрос банка.

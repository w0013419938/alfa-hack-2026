# Допущения и упрощения

Здесь собраны решения, принятые там, где ТЗ оставляет свободу, и упрощения прототипа.
Каждое — с обоснованием.

## Инфраструктура и запуск

1. **Имя compose-проекта задано явно** (`name: credit-cabinet` в `docker-compose.yml`).
   Если папка репозитория названа кириллицей, Docker Compose не может вывести имя проекта и не запускается.
2. **Порт PostgreSQL наружу не публикуется.** У жюри может быть свой PostgreSQL на 5432 — конфликт портов сломал бы запуск.
   Подключиться к базе можно так: `docker compose exec db psql -U credit -d credit_cabinet`.
3. **Значения по умолчанию прямо в `docker-compose.yml`** (`${VAR:-default}`), а `.env` необязателен.
   Требование «запуск без ручных шагов» важнее: жюри не должно копировать `.env`. Демо-секрет JWT
   помечен как небезопасный; при `APP_ENV=production` бэкенд с ним не запустится.
4. **Dev-зависимости (pytest) входят в образ бэкенда**, чтобы тесты запускались командой
   `docker compose run --rm backend uv run pytest` без отдельного образа. В продакшене стоит собрать отдельный образ без них.
5. **Тесты используют отдельную базу** `<имя базы>_test` на том же сервере PostgreSQL и настоящий `mock-external`.
   Тестовая база пересоздаётся при каждом запуске тестов, демо-данные основной базы не затрагиваются.

## Данные и справочники

6. **Продукты хранятся в таблице `products`, но источник истины — `config/products.yaml`.** При каждом старте таблица
   обновляется из файла. Продукт, удалённый из файла, не удаляется из БД (на него могут ссылаться заявки), а выключается.
7. **Компании и пользователи из seed добавляются только если их ещё нет** (по ИНН и логину). Изменения в seed-файлах
   применяются после `docker compose down -v`. Так повторный старт гарантированно ничего не дублирует и не затирает.
8. **Демо-пароли по правилу `<логин>123`** (из ТЗ). Хешируются bcrypt при seed, в репозитории паролей в открытом виде нет,
   кроме описания правила в README.
9. **ИНН синтетические, но с правильной контрольной суммой** — иначе их отбросила бы проверка ИНН.
10. **Идентификаторы — UUID**, чтобы id заявок нельзя было перебрать. Для людей у заявки есть короткий номер (`number`, с 1001).
11. **Деньги в БД — `NUMERIC`, в API — числа** (не строки), так удобнее фронтенду.

## Безопасность

12. **Ограничение попыток входа хранится в памяти процесса** (5 неудачных попыток за 60 секунд на пару «IP + логин» → 429).
    Допустимо по ТЗ. При нескольких экземплярах бэкенда счётчик нужно вынести в Redis.
13. **Для несуществующего логина всё равно проверяется bcrypt-хеш-заглушка**, чтобы по времени ответа нельзя было
    узнать, какие логины существуют.
14. **Токен передаётся в заголовке `Authorization: Bearer`**, refresh-токенов нет: срок жизни access-токена 60 минут
    (настраивается). Для прототипа достаточно; в продакшене — refresh-токены или сессии через SSO банка.
15. **Access-лог uvicorn отключён**: он пишет IP-адреса. Вместо него свой журнал запросов: метод, путь (без query), статус,
    длительность, request id.

## Процесс и бизнес-логика

16. **Отозвать заявку можно в статусах DRAFT, NEEDS_INFO и MANUAL_REVIEW**, то есть до решения банка. Пока идёт
    автоматическая обработка (несколько секунд), отзыв недоступен — это упрощает пайплайн.
17. **От предложения можно отказаться и после принятия, но до подписания** (OFFER_ACCEPTED → CLIENT_DECLINED).
18. **Анкету в статусе NEEDS_INFO клиент правит через тот же `PATCH`, что и черновик**, затем нажимает `provide_info`.
    Если банк запросил документы, `provide_info` недоступен (кнопка с `enabled: false` и причиной), пока они не загружены.
19. **Идемпотентность действий**: если действие уже недоступно, но последнее «человеческое» событие заявки — это то же
    действие того же пользователя, API возвращает текущее состояние (200), а не 409. Так двойной клик или повтор запроса
    после обрыва связи ничего не ломают. Отдельные ключи идемпотентности (`Idempotency-Key`) не вводили — для прототипа избыточно.
20. **Оптимистичная блокировка**: каждая заявка имеет `version`. Если клиент передал `version` и она устарела — 409.
    Плюс все изменения статуса идут под `SELECT ... FOR UPDATE`.
21. **Текущие платежи по кредитам = большее из анкеты и БКИ** (консервативная оценка). DTI считается по выручке из анкеты,
    как в ТЗ: (текущие платежи + новый платёж по базовой ставке) / месячная выручка.
22. **Если БКИ или ЕГРЮЛ не ответили, скоринг всё равно считается** (факторы без данных получают `missing_points`),
    а решение — «ручное рассмотрение». Так у сотрудника в карточке есть хотя бы частичная оценка.
    Стоп-факторы по уже полученным данным (например, ликвидация по ЕГРЮЛ) срабатывают и при сбое БКИ.
23. **«Компания не найдена в ЕГРЮЛ» (404 от реестра) — это ответ, а не сбой**: стоп-фактор и отказ.
24. **Правило «не хватает данных»** (decision.yaml → `needs_info`): если у компании нет годовой выручки по отчётности,
    банк просит выписку по счёту. Это детерминированно даёт сценарий `client_info` независимо от того, что введено в анкете.
25. **Встречное предложение**: сначала пробуем сохранить сумму (для грейда C — 70% от запрошенной), увеличивая срок
    с шагом 6 мес. до максимума продукта; если не выходит — уменьшаем сумму до доступной при допустимой нагрузке.
    Если и это ниже минимальной суммы продукта — ручное рассмотрение (настраивается).
26. **Грейд E — отказ**, грейд D — ручное рассмотрение (в ТЗ «пограничный»), C — встречное предложение, A и B — одобрение.
27. **Сотрудник может одобрить с изменёнными условиями**. Если сумма и срок совпадают с запрошенными — тип предложения
    `as_requested`, иначе `counter_offer`. Ставка не может быть ниже базовой ставки продукта.
28. **Комментарий сотрудника виден клиенту** в истории заявки. Внутренние технические детали (payload событий: причины
    решения с кодами, статусы проверок) видит только сотрудник.
29. **Предложение действует 30 дней** (decision.yaml). Истёкшее предложение нельзя принять; автоматического перевода
    заявки в другой статус по истечении срока нет — для демо не нужен.
30. **Подписание — имитация**: подтверждение действием `sign`, договор формируется в HTML по шаблону (без PDF-библиотек,
    чтобы не тянуть лишние зависимости) и сохраняется как документ. Выдача — событие `issue` с суммой, без реальных операций.
31. **Справочники, продукты, калькулятор и подбор продукта доступны без входа**: в них нет персональных данных,
    а фронту удобно показывать их на стартовой странице до логина.

## Надёжность

32. **Фоновая обработка — пул потоков внутри процесса бэкенда** (`ThreadPoolDispatcher`). Пайплайн устроен «по статусам»,
    поэтому при старте бэкенд возобновляет заявки, застрявшие в автоматических статусах (например, после перезапуска).
    В продакшене нужна очередь (RabbitMQ/Kafka) и отдельные воркеры — достаточно реализовать другой диспетчер.
33. **Если шаг пайплайна упал с неожиданной ошибкой**, заявка уходит на ручное рассмотрение (`technical_error`), а не «зависает».
34. **Размер загружаемого файла проверяется в приложении** после приёма запроса. В продакшене лимит размера тела запроса
    нужно ставить ещё и на прокси (nginx/ingress), чтобы большие запросы отсекались до приложения.
35. **Файлы хранятся в Docker volume `uploads`.** Для нескольких экземпляров бэкенда нужно объектное хранилище (S3-совместимое).

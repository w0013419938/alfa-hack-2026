# Допущения и упрощения

Здесь записаны решения, которые пришлось принять там, где ТЗ оставляет свободу, и упрощения прототипа. У каждого есть причина. Номера пунктов не меняются, на них ссылаются другие документы.

## Инфраструктура и запуск

1. Имя compose-проекта задано явно: `name: credit-cabinet` в `docker-compose.yml`. Если папка репозитория названа кириллицей, Docker Compose не может сам вывести имя проекта и не запускается.
2. Порт PostgreSQL наружу не опубликован. У жюри на 5432 может работать свой PostgreSQL, и конфликт портов сломал бы запуск. К базе можно подключиться так: `docker compose exec db psql -U credit -d credit_cabinet`.
3. Значения по умолчанию записаны прямо в `docker-compose.yml` (`${VAR:-default}`), а `.env` не обязателен. Запуск без ручных шагов важнее: жюри не должно копировать `.env`. Демо-секрет JWT помечен как небезопасный, и при `APP_ENV=production` бэкенд с ним не запустится.
4. Dev-зависимости (pytest) входят в образ бэкенда. Так тесты запускаются командой `docker compose run --rm backend uv run pytest` без отдельного образа. Для продакшена стоит собирать образ без них.
5. Тесты работают с отдельной базой `<имя базы>_test` на том же сервере PostgreSQL и с настоящим `mock-external`. Тестовая база пересоздаётся при каждом запуске, демо-данные основной базы остаются нетронутыми.

## Данные и справочники

6. Продукты лежат в таблице `products`, но главный источник для них `config/products.yaml`. При каждом старте таблица обновляется из файла. Продукт, удалённый из файла, в базе не удаляется (на него могут ссылаться заявки), а выключается.
7. Компании и пользователи из seed добавляются, только если их ещё нет (проверка по ИНН и логину). Чтобы применить изменения в seed-файлах, нужен `docker compose down -v`. Зато повторный старт ничего не дублирует и не затирает.
8. Демо-пароли строятся по правилу из ТЗ: логин плюс `123`. При seed они хешируются bcrypt. Открытых паролей в репозитории нет, есть только описание правила в README.
9. ИНН синтетические, но с правильной контрольной суммой, иначе их отбросила бы проверка ИНН.
10. Идентификаторы сделаны UUID, чтобы id заявок нельзя было перебрать. Для людей у заявки есть короткий номер `number`, он начинается с 1001.
11. Деньги хранятся в базе как `NUMERIC`, а в API отдаются числами, не строками. Фронту так удобнее.

## Безопасность

12. Счётчик неудачных попыток входа хранится в памяти процесса: 5 попыток за 60 секунд на пару «IP + логин», дальше 429. ТЗ это допускает. Если экземпляров бэкенда несколько, счётчик нужно вынести в Redis.
13. Если логина не существует, бэкенд всё равно проверяет пароль против bcrypt-хеша-заглушки. Иначе по времени ответа можно было бы узнать, какие логины есть в системе.
14. Токен передаётся в заголовке `Authorization: Bearer`, refresh-токенов нет. Access-токен живёт 60 минут, срок настраивается. Прототипу этого хватает. В продакшене понадобятся refresh-токены или сессии через SSO банка.
15. Access-лог uvicorn отключён, потому что он пишет IP-адреса. Вместо него бэкенд ведёт свой журнал запросов: метод, путь без query, статус, длительность и request id.

## Процесс и бизнес-логика

16. Отозвать заявку можно в статусах DRAFT, NEEDS_INFO и MANUAL_REVIEW, то есть до решения банка. Пока идёт автоматическая обработка (несколько секунд), отзыв недоступен. Так пайплайн проще.
17. От предложения можно отказаться и после того, как его приняли, но только до подписания (OFFER_ACCEPTED → CLIENT_DECLINED).
18. Анкету в статусе NEEDS_INFO клиент правит тем же `PATCH`, что и черновик, а потом нажимает `provide_info`. Если банк запросил документы, `provide_info` недоступен, пока их не загрузят: кнопка приходит с `enabled: false` и причиной.
19. Повтор действия. Бывает, что действие уже недоступно, но последнее действие человека по заявке точно такое же и от того же пользователя, а заявка всё ещё в статусе, куда это действие её привело, или в автоматической обработке после него. Тогда API возвращает текущее состояние с кодом 200, а не 409. Двойной клик или повтор запроса после обрыва связи ничего не ломают. Если процесс уже дошёл до нового решения (NEEDS_INFO, OFFER_SENT, финальный статус), повтор считается новой попыткой и получает 409. Отдельные ключи идемпотентности (`Idempotency-Key`) прототипу не нужны.
20. Оптимистичная блокировка: у каждой заявки есть `version`. Если клиент передал `version`, а она устарела, придёт 409. Кроме того, все изменения статуса идут под `SELECT ... FOR UPDATE`.
21. Текущие платежи по кредитам берутся как большее из двух чисел: из анкеты и из БКИ. Это осторожная оценка. Долговая нагрузка (DTI) считается по выручке из анкеты, как в ТЗ: текущие платежи плюс новый платёж по базовой ставке, делённые на месячную выручку.
22. Если БКИ или ЕГРЮЛ не ответили, скоринг всё равно считается: факторы без данных получают `missing_points`. Решением в этом случае будет ручное рассмотрение, и у сотрудника в карточке есть хотя бы частичная оценка. Стоп-факторы по уже полученным данным срабатывают и при сбое БКИ. Например, ликвидация по ЕГРЮЛ даст отказ.
23. Ответ реестра «компания не найдена» (404) считается ответом, а не сбоем. Это стоп-фактор и отказ.
24. Правило «не хватает данных» лежит в `decision.yaml` (`needs_info`). Если у компании нет годовой выручки по отчётности, банк просит выписку по счёту. На этом правиле держится сценарий `client_info`, и он срабатывает при любой анкете.
25. Встречное предложение подбирается так. Сначала система пытается сохранить сумму (для грейда C это 70% от запрошенной) и увеличивает срок шагами по 6 месяцев до максимума продукта. Если так не выходит, сумма уменьшается до той, что укладывается в допустимую нагрузку. Если и она ниже минимальной суммы продукта, заявка уходит на ручное рассмотрение (это настраивается).
26. По грейдам: A и B одобряются, C получает встречное предложение, D уходит специалисту (в ТЗ это «пограничный» случай), E получает отказ.
27. Сотрудник может одобрить заявку с изменёнными условиями. Если сумма и срок совпали с запрошенными, тип предложения `as_requested`, иначе `counter_offer`. Ставку ниже базовой ставки продукта поставить нельзя.
28. Комментарий сотрудника клиент видит в истории заявки. Технические подробности (payload событий с кодами причин решения и статусами проверок) видит только сотрудник.
29. Предложение действует 30 дней, срок задан в `decision.yaml`. Истёкшее предложение принять нельзя. Автоматически переводить такую заявку в другой статус для демо не нужно, поэтому этого нет.
30. Подписание имитируется действием `sign`. Договор собирается в HTML по шаблону и сохраняется как документ; PDF-библиотеки не подключали, чтобы не тянуть лишние зависимости. Выдача денег тоже имитируется: это событие `issue` с суммой, без реальных операций.
31. Справочники, продукты, калькулятор и подбор продукта доступны без входа. Персональных данных в них нет, а фронт может показывать их ещё до логина.

## Надёжность

32. Фоновая обработка идёт в пуле потоков внутри процесса бэкенда (`ThreadPoolDispatcher`). Каждый шаг пайплайна опирается на текущий статус заявки, поэтому при старте бэкенд просто возобновляет заявки, застрявшие в автоматических статусах. В продакшене нужны очередь (RabbitMQ, Kafka) и отдельные воркеры, для этого достаточно написать другой диспетчер.
33. Если шаг пайплайна упал с неожиданной ошибкой, заявка уходит на ручное рассмотрение (`technical_error`) и не зависает.
34. Размер загружаемого файла проверяет приложение уже после того, как приняло запрос. В продакшене лимит на размер тела запроса нужно ставить ещё и на прокси (nginx, ingress), чтобы большие запросы не доходили до приложения.
35. Файлы хранятся в Docker volume `uploads`. Для нескольких экземпляров бэкенда нужно S3-совместимое хранилище.

## Интеграции и данные

36. ФНС «Прозрачный бизнес» отдельным сервисом не моделировали. В ТЗ для мока названы только ЕГРЮЛ/ЕГРИП и БКИ, а отрасль и выручку бэкенд берёт из профиля компании и анкеты. Добавить такой мок можно по образцу `mock-external` и `ExternalDataClient`.
37. Для ИНН, которого нет в `external_mocks.json`, мок собирает ответ из самого ИНН, всегда одинаковый для одного ИНН (так требует ТЗ). Поэтому заявка любой новой компании тоже проходит весь путь.
38. К режимам сбоя `timeout` и `error` добавлен `flaky`: каждый нечётный запрос по ИНН падает с 503. Так в демо-истории видно, как повтор запроса проходит успешно. Счётчик запросов живёт в памяти мока и обнуляется при его перезапуске.
39. Во всех сценариях жюри используется одна анкета (`docs/test-scenarios.md`). Исход зависит от данных компании (ЕГРЮЛ, БКИ, отрасль, отчётность), а не от того, что ввёл проверяющий, поэтому сценарии воспроизводятся.
40. Демо-история заявок (`seed/applications.json`) создаётся через настоящий пайплайн при первом запуске. Если мок в этот момент недоступен, эти заявки уйдут на ручное рассмотрение. Основные сценарии от этого не зависят, это фоновые данные.
41. Возраст бизнеса считается от текущей даты, так что через несколько лет баллы демо-компаний изменятся. Даты регистрации подобраны под дату сдачи, октябрь 2026.

## API

42. Статус заявки фронт узнаёт опросом `GET /applications/{id}` раз в 3 секунды. WebSocket и SSE записаны в «Идеи на потом».
43. Пагинация устроена через `page` и `page_size` (до 100), ответ имеет вид `{items, total, page, page_size}`.
44. Health-эндпоинты живут под тем же префиксом: `/api/v1/health` и `/api/v1/ready`.
45. Скоринг считает долговую нагрузку по базовой ставке продукта, потому что итоговая ставка ещё неизвестна. Кредитное решение потом перепроверяет нагрузку по ставке предложения с надбавкой за грейд.
46. Если уточнения запрашивал сотрудник, после ответа клиента решение снова принимает он. Заявка ещё раз проходит проверки и скоринг, чтобы у сотрудника были свежие данные, но итогом всегда будет `MANUAL_REVIEW` с причиной «клиент ответил на запрос специалиста». Стоп-факторы по-прежнему дают автоматический отказ. Без этого клиент мог бы «поправить» анкету (выручку из анкеты не с чем сверить) и обойти ручное рассмотрение.
47. В бэкенде работает фоновый поток-сторож. Раз в 60 секунд он возобновляет заявки, которые дольше 120 секунд стоят в автоматическом статусе. Это страховка на случай, если погиб поток или база была недоступна. При нескольких экземплярах сторожей будет несколько. Это безопасно, потому что шаги проверяют статус под блокировкой, хотя лишние запросы к внешним сервисам возможны. В продакшене эту роль возьмёт повторная доставка сообщений из очереди.
48. На одну заявку можно загрузить не больше 20 документов (`MAX_DOCUMENTS_PER_APPLICATION`), чтобы одной заявкой нельзя было заполнить диск.
49. Swagger UI и ReDoc загружают оформление с CDN jsDelivr. Версии закреплены: swagger-ui-dist 5.17.14 и redoc 2.1.5. Это касается только страниц документации в браузере. Сам API работает без интернета, схема лежит в `docs/openapi.json`. Встраивать статику Swagger в репозиторий для прототипа не стали.
50. Номер страницы ограничен 100 000. Иначе огромное значение приводило бы к ошибке базы вместо понятного 422.

## Фронтенд

51. Стиль взят из Figma команды (файл «кейс-школа-альфа», слайды «Метронома»). Перенесён только визуальный язык, содержание слайдов в интерфейсе не используется. Значения сняты прямо из макета: акцент `#EF3124`, текст `#222`, салатовый `#8FEE52`, фон `#F4F5F7`, карточки со скруглением 32px, плашки 16–24px. Фиолетовый в макете встречается только на 3D-картинках, поэтому его значение `#9B5CFF` взято из ТЗ. Всё собрано в `frontend/src/theme.ts`.
52. Шрифт Golos Text, а не Inter. В ТЗ указан Inter, но в Figma везде Golos Text, а дизайн просили перенести из Figma. Шрифт подключён локально через `@fontsource/golos-text` (лицензия OFL) и интернета не требует.
53. Шкалу этапов отдаёт бэкенд в поле `progress`, для этого его пришлось доработать. Если бы фронт сам сопоставлял статусы с этапами, он повторял бы логику процесса: NEEDS_INFO бывает на разных этапах, а отзыв заявки останавливает процесс где угодно.
54. Пока заявка не в финальном статусе, фронт опрашивает её каждые 3 секунды (TanStack Query, `refetchInterval`). Очередь сотрудника обновляется раз в 5 секунд, статистика раз в 10.
55. Какие действия доступны, решает только API: кнопки рисуются из `available_actions`. Фронт решает лишь, как их показать. Для некоторых кодов он открывает форму или окно, а не вызывает API сразу: `edit` ведёт к анкете, `upload_document` к блоку документов, `sign` открывает окно с договором, `provide_info` окно с комментарием, а при `confirm_text` показывается подтверждение.
56. Фронт проверяет анкету только для удобства: заполнены ли поля и укладываются ли сумма и срок в лимиты продукта из `/products`. Окончательно анкету проверяет бэкенд, и его сообщение показывается как есть.
57. Токен хранится в `localStorage`. Для прототипа этого достаточно. В продакшене нужны httpOnly-cookie и защита от XSS и CSRF.
58. Фронт ходит в API через nginx по тому же адресу (`/api` проксируется на backend), поэтому CORS не нужен. Swagger тоже открывается через фронт: http://localhost:3000/docs.
59. E2E-тесты Playwright запускаются отдельным сервисом `e2e` в профиле compose. Так обычный `docker compose up` не скачивает образ с браузером.

## Дизайн-проход

60. Стиль экранов `pastel-consumer` из скила `/design-taste-frontend` взят только по композиции и иерархии. Цвета и шрифт остались из `theme.ts`. Иконочный рейл вместо шапки не делали: в макете Альфы верхняя шапка, разделов по два, а перестройка каркаса перед сдачей рискованна.
61. Новых библиотек не добавлено. Шкала этапов, полосы скоринга и нагрузки, скелетоны и анимации сделаны на CSS и компонентах Mantine. Слайдеры калькулятора тоже из Mantine.
62. 3D-молния на экране входа выгружена из Figma команды («кейс-школа-альфа») и хранится в репозитории (`frontend/src/assets/lightning-3d.png`, 640px). CDN не нужен.
63. Полоса долговой нагрузки рисуется только у сотрудника и без отметки предела. Порог есть только в `backend/config/decision.yaml`, в API его нет, а хардкодить его во фронте нельзя по правилам проекта.
64. Цвет грейда в очереди и сводке идёт по одной шкале: A и B зелёные, C чернильный, D и E красные. Буквы грейдов заданы в `scoring.yaml`; если появится новая буква, она будет чернильной.
65. Порядок «главных рисков» в сводке сотрудника фронт получает сортировкой факторов из API по потерянным баллам. Это вид, а не вычисление: числа не меняются.

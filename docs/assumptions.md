# Допущения и упрощения

Здесь собраны решения, принятые там, где ТЗ оставляет свободу, и упрощения прототипа.
Каждое — с обоснованием.

## Инфраструктура и запуск

1. **Имя compose-проекта задано явно** (`name: credit-cabinet` в `docker-compose.yml`).
   Если папка репозитория названа кириллицей, Docker Compose не может вывести имя проекта и не запускается.
2. **Порт PostgreSQL наружу не публикуется.** У жюри может быть свой PostgreSQL на 5432 — конфликт портов сломал бы запуск.
   Подключиться к базе можно так: `docker compose exec db psql -U credit -d credit_cabinet`.
3. **Значения по умолчанию прямо в `docker-compose.yml`** (`${VAR:-default}`), а `.env` необязателен.
   Требование «запуск без ручных шагов» важнее: жюри не должно копировать `.env`. Демо-секрет JWT
   помечен как небезопасный; при `APP_ENV=production` бэкенд с ним не запустится.
4. **Dev-зависимости (pytest) входят в образ бэкенда**, чтобы тесты запускались командой
   `docker compose run --rm backend uv run pytest` без отдельного образа. В продакшене стоит собрать отдельный образ без них.
5. **Тесты используют отдельную базу** `<имя базы>_test` на том же сервере PostgreSQL и настоящий `mock-external`.
   Тестовая база пересоздаётся при каждом запуске тестов, демо-данные основной базы не затрагиваются.

## Данные и справочники

6. **Продукты хранятся в таблице `products`, но источник истины — `config/products.yaml`.** При каждом старте таблица
   обновляется из файла. Продукт, удалённый из файла, не удаляется из БД (на него могут ссылаться заявки), а выключается.
7. **Компании и пользователи из seed добавляются только если их ещё нет** (по ИНН и логину). Изменения в seed-файлах
   применяются после `docker compose down -v`. Так повторный старт гарантированно ничего не дублирует и не затирает.
8. **Демо-пароли по правилу `<логин>123`** (из ТЗ). Хешируются bcrypt при seed, в репозитории паролей в открытом виде нет,
   кроме описания правила в README.
9. **ИНН синтетические, но с правильной контрольной суммой** — иначе их отбросила бы проверка ИНН.
10. **Идентификаторы — UUID**, чтобы id заявок нельзя было перебрать. Для людей у заявки есть короткий номер (`number`, с 1001).
11. **Деньги в БД — `NUMERIC`, в API — числа** (не строки), так удобнее фронтенду.

## Безопасность

12. **Ограничение попыток входа хранится в памяти процесса** (5 неудачных попыток за 60 секунд на пару «IP + логин» → 429).
    Допустимо по ТЗ. При нескольких экземплярах бэкенда счётчик нужно вынести в Redis.
13. **Для несуществующего логина всё равно проверяется bcrypt-хеш-заглушка**, чтобы по времени ответа нельзя было
    узнать, какие логины существуют.
14. **Токен передаётся в заголовке `Authorization: Bearer`**, refresh-токенов нет: срок жизни access-токена 60 минут
    (настраивается). Для прототипа достаточно; в продакшене — refresh-токены или сессии через SSO банка.
15. **Access-лог uvicorn отключён**: он пишет IP-адреса. Вместо него свой журнал запросов: метод, путь (без query), статус,
    длительность, request id.

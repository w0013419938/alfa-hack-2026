Тебе предстоит с нуля построить бэкенд для прототипа на хакатоне. Это длинная многоэтапная задача: работай автономно, пока всё не будет готово и проверено.

<context>
Мы команда из 5 человек на хакатоне Альфа-Банка, кейс «Умный кредитный кабинет предпринимателя». Сдача 26.10.2026, времени мало. Я отвечаю за всю разработку, остальные участники готовят исследование, правила скоринга, параметры продуктов и синтетический датасет, но ещё не закончили.

Жюри будет проверять решение само: клонирует репозиторий, запустит `docker compose up --build` на обычном ноутбуке, прочитает README и пройдёт сценарии. Поэтому для нас важнее всего три вещи, в таком порядке:
1. Сквозной сценарий надёжно работает от создания заявки до финального статуса.
2. Запуск с нуля одной командой без ручных шагов, и README, по которому можно всё проверить.
3. Enterprise-подход, который жюри оценивает отдельно: безопасность, надёжность, отказоустойчивость, понятная архитектура.

Фронтенд будет отдельной задачей позже, поэтому API должен быть удобен для фронта: фронт только отображает то, что прислал бэкенд.
</context>

<spec>
Полное техническое задание лежит в `TASK_BACKEND.md`, а краткие правила проекта в `CLAUDE.md`. Прочитай оба файла целиком, прежде чем писать код. ТЗ — источник истины по стеку, структуре репозитория, сущностям, статусам, API, пайплайну, тестам и документации.
</spec>

<how_to_work>
Начни с плана. Изучи ТЗ и составь план реализации по этапам из раздела «Порядок работы» ТЗ. Запиши его в `docs/PROGRESS.md` как чек-лист. После этого сразу переходи к реализации, не дожидаясь моего подтверждения.

Веди состояние так, чтобы работу можно было продолжить с любого места. Это важно, потому что задача длинная и контекст может обновиться:
- после каждого этапа отмечай его в `docs/PROGRESS.md` и коротко записывай, что сделано, что осталось и какие есть известные проблемы;
- после каждого этапа делай отдельный git-коммит с понятным сообщением;
- если начинаешь работу с новым контекстом, первым делом прочитай `CLAUDE.md`, `docs/PROGRESS.md` и `git log`, а потом продолжай с первого незавершённого этапа.

Проверяй каждый этап по-настоящему. Запускай тесты и контейнеры и обращайся к эндпоинтам реальными запросами. Не считай этап готовым, пока он не работает в `docker compose up --build`.

Тесты должны проверять реальное поведение. Если тест падает, исправляй код, а не тест. Не подгоняй реализацию под конкретные тестовые входные данные и не хардкодь ожидаемые результаты. Если считаешь, что сам тест неправильный, напиши об этом в `docs/PROGRESS.md` и объясни почему.

Делай то, что просит ТЗ, и не больше. Не добавляй функции, слои абстракции и библиотеки, которых нет в ТЗ: код будут поддерживать джуниор-разработчики, и каждая лишняя абстракция мешает им. Если видишь полезное улучшение, запиши его в раздел «Идеи на потом» в `docs/PROGRESS.md`, а не реализуй.

Когда информации не хватает, не останавливайся с вопросом. Прими разумное решение, которое лучше всего служит сквозному сценарию, и запиши его в `docs/assumptions.md` с обоснованием. Остановись и спроси меня только в одном случае: если действие удаляет данные или файлы вне этого репозитория либо его нельзя откатить через git.

Данные, которые готовят коллеги (продукты, правила скоринга, пороги, тексты статусов, демо-компании), бери из конфигов `backend/config/` и `backend/seed/` с правдоподобными значениями-заглушками и пометкой `TODO(участник N)`. Когда коллеги пришлют настоящие значения, мы будем менять только эти файлы.

Если несколько действий не зависят друг от друга (прочитать несколько файлов, запустить независимые проверки), выполняй их параллельно.
</how_to_work>

<definition_of_done>
- `docker compose down -v && docker compose up --build` на чистой машине поднимает db, mock-external и backend без ручных шагов; миграции и seed применяются автоматически и идемпотентно.
- Для каждой тестовой учётки из ТЗ сквозной сценарий через API приводит к ожидаемому исходу: одобрение, встречное предложение, ручное рассмотрение, отказ, запрос уточнений, сбой БКИ.
- Каждый ответ с заявкой содержит `status_label`, `status_description`, `available_actions` и `timeline`.
- Все тесты зелёные.
- Есть README, `THIRD_PARTY_NOTICES.md`, `docs/architecture.md`, `docs/state-diagram.md`, `docs/data-model.md`, `docs/api.md`, `docs/openapi.json`, коллекция запросов в `docs/requests/`, `docs/test-scenarios.md`, `docs/assumptions.md`.
- Версии зафиксированы lock-файлами.
</definition_of_done>

# Задача для Claude Code: бэкенд «Умный кредитный кабинет предпринимателя»

## Контекст

Мы делаем прототип для хакатона Альфа-Банка (кейс «Умный кредитный кабинет предпринимателя»). Сдача 26.10.2026.

Продукт — цифровой кредитный конвейер для малого и микробизнеса, который объединяет клиентский путь и внутреннюю обработку заявки:

- **Клиент** (предприниматель без банковской экспертизы) выбирает кредитный продукт, подаёт заявку, видит статус и понятные следующие шаги, получает и принимает предложение.
- **Сотрудник банка** (андеррайтер) видит очередь заявок, результаты проверок и скоринга, принимает решение по пограничным случаям.

Сейчас нужен **только бэкенд + инфраструктура**. Фронтенд будет позже, отдельной задачей. Сделай бэкенд так, чтобы фронту было максимально просто: фронт не должен сам вычислять логику процесса.

### Жёсткие ограничения организаторов

- Запуск в Docker, единый воспроизводимый способ поднять всё на обычном ПК: `docker compose up --build`.
- Версии языка и библиотек зафиксированы lock-файлами.
- Никаких платных API, подписок, покупных данных. Никакого доступа к реальным системам банка.
- Все внешние сервисы (БКИ, ЕГРЮЛ/ЕГРИП, ФНС «Прозрачный бизнес») — локальные моки с сохранением смысла интеграции.
- Только синтетические данные.
- Подписание документов и выдача денег — имитация, без реальных операций.
- Весь сценарий внутри продукта: никаких email, SMS, мессенджеров.
- Если когда-либо понадобится LLM — только модели с открытыми весами (в этой задаче LLM не нужен).
- Жюри оценивают enterprise-подход: безопасность, надёжность, отказоустойчивость, масштабирование, сопровождаемость.

### Важно: часть входных данных ещё не готова

Коллеги ещё дорабатывают:
- **параметры продуктов и правила скоринга** (участник 2);
- **финальную модель процесса и синтетический датасет** (участник 3).

Поэтому **все продуктовые параметры, правила скоринга, пороги решений и демо-данные вынеси в конфигурационные файлы** (`backend/config/*.yaml`, `backend/seed/*.json`) с разумными значениями-заглушками и комментарием `# TODO(участник 2)` / `# TODO(участник 3)`. Код не должен меняться, когда они пришлют настоящие значения — только конфиги.

Не задавай мне вопросов. Где не хватает информации — прими разумное решение и запиши его в `docs/assumptions.md`.

## Предметная модель

### Роли
- `client` — представитель компании; видит только заявки своей компании.
- `employee` — сотрудник банка; видит все заявки, принимает решения.

### Сущности (минимум)
- `User` — логин, хеш пароля, ФИО, роль, `company_id` (для клиента), должность в компании (собственник, директор, бухгалтер и т. п.).
- `Company` — ИНН, ОГРН/ОГРНИП, тип (ООО / ИП), название, ОКВЭД (основной), отрасль, дата регистрации, регион, выручка за год, численность.
- `Product` — загружается из `config/products.yaml`: код, название, понятное описание «для чего подходит», мин/макс сумма, мин/макс срок, базовая ставка, нужен ли залог, список обязательных полей заявки.
- `Application` — компания, автор, продукт, сумма, срок, цель (из справочника + свободный текст), финансовые данные из анкеты (месячная выручка, расходы, текущие ежемесячные платежи по кредитам), статус, версия (optimistic locking), даты.
- `ApplicationEvent` — история: из какого статуса в какой, кто (пользователь или `system`), когда, комментарий, payload. Это и аудит, и таймлайн для клиента.
- `ExternalCheck` — тип (`egrul`, `bki`), запрос, ответ, статус (ok / error / timeout), время.
- `ScoringResult` — итоговый балл, грейд риска, вклад каждого фактора (для объяснимости), версия правил.
- `Offer` — сумма, срок, ставка, ежемесячный платёж, тип (`as_requested` / `counter_offer`), срок действия, статус.
- `InfoRequest` — что именно банк просит уточнить (список полей/документов + комментарий), ответ клиента.
- `Document` — загруженные клиентом файлы (хранить на диске/volume, метаданные в БД; разрешённые типы и макс. размер ограничены).

Нарисуй ER-диаграмму в `docs/data-model.md` (Mermaid).

### Статусы заявки и машина состояний

| Статус | Смысл |
|---|---|
| `DRAFT` | черновик, клиент заполняет |
| `SUBMITTED` | отправлена |
| `VALIDATION` | автопроверка полноты и корректности |
| `NEEDS_INFO` | банк запросил уточнения, ждём клиента |
| `CHECKS` | запросы во внешние источники (ЕГРЮЛ, БКИ) |
| `SCORING` | скоринг |
| `MANUAL_REVIEW` | пограничный случай, у сотрудника |
| `OFFER_SENT` | клиенту отправлено предложение (как запрошено или на изменённых условиях) |
| `OFFER_ACCEPTED` | клиент принял условия |
| `SIGNING` | имитация подписания документов |
| `ISSUED` | имитация выдачи средств — финал |
| `REJECTED` | отказ — финал |
| `CLIENT_DECLINED` | клиент отказался от предложения — финал |
| `CANCELLED` | клиент отозвал заявку до решения — финал |

Требования:
- Машина состояний описана **в одном месте** (`app/domain/state_machine.py`) как таблица переходов: `(из статуса, действие) → в статус`, кто может выполнять (`client` / `employee` / `system`), предусловия.
- Любая смена статуса идёт только через неё, атомарно, с записью `ApplicationEvent`. Недопустимый переход → `409 Conflict` с понятным сообщением.
- Конкурентные изменения защищены (версия заявки / `SELECT ... FOR UPDATE`).
- Нарисуй диаграмму состояний в `docs/state-diagram.md` (Mermaid `stateDiagram-v2`).

### `available_actions` — ключевое для фронта

Каждый ответ с заявкой содержит:
- `status` и `status_label` — понятное клиенту название на русском;
- `status_description` — одна-две фразы простым языком: что сейчас происходит и что будет дальше;
- `available_actions` — список действий, доступных **текущему пользователю** сейчас (например `edit`, `submit`, `cancel`, `provide_info`, `accept_offer`, `decline_offer`, `sign`, а для сотрудника `approve`, `counter_offer`, `request_info`, `reject`), каждое с `label` на русском;
- `timeline` — события истории в понятном виде;
- для `NEEDS_INFO` — что именно нужно предоставить.

Тексты статусов и действий вынеси в `config/labels.yaml`, чтобы участник 1 мог их переписать без правок кода.

## Пайплайн обработки заявки

После `submit` запускается автообработка (фоновая задача; сделай так, чтобы её можно было позже вынести в очередь — например, через интерфейс-диспетчер):

1. **VALIDATION** — проверка полноты и корректности по правилам продукта: сумма и срок в пределах продукта, заполнены обязательные поля, ИНН корректен (контрольная сумма), числовые поля разумны. Ошибки → `NEEDS_INFO` с перечнем, что исправить.
2. **CHECKS** — запросы в `mock-external`:
   - ЕГРЮЛ/ЕГРИП: существование, статус (действующая / ликвидирована / в процессе ликвидации), дата регистрации, ОКВЭД, руководитель;
   - БКИ: кредитная история — действующие обязательства, суммы, ежемесячные платежи, просрочки (количество, максимальная длительность), кредитный рейтинг бюро.

   Клиент к интеграциям: таймауты, ретраи с backoff, обработка ошибок. Если внешний сервис недоступен после ретраев — заявка уходит в `MANUAL_REVIEW` с пометкой, а не падает.
3. **SCORING** — балльная модель по `config/scoring.yaml`: список факторов, для каждого — источник значения, диапазоны и баллы. Примеры факторов-заглушек: возраст бизнеса, долговая нагрузка (DTI = (текущие платежи + новый платёж) / месячная выручка), наличие и длительность просрочек, рейтинг БКИ, отношение запрашиваемой суммы к годовой выручке, отрасль. Результат: балл, грейд (A–E), **вклад каждого фактора** с понятным объяснением.
4. **Кредитное решение** (`app/domain/decision.py`, правила из `config/decision.yaml`) — отдельно от скоринга, учитывает грейд, продукт, сумму, срок и стоп-факторы:
   - стоп-факторы (компания ликвидирована, текущая просрочка > N дней, и т. п.) → `REJECTED` с понятной причиной;
   - хороший грейд → `OFFER_SENT` с предложением `as_requested`;
   - средний грейд или превышение допустимой нагрузки → `OFFER_SENT` с `counter_offer` (система подбирает максимальную сумму / другой срок, при которых нагрузка в норме);
   - пограничный грейд или ошибки интеграций → `MANUAL_REVIEW`;
   - не хватает данных → `NEEDS_INFO`.
5. **Расчёт предложения** — ставка = базовая ставка продукта + надбавка по грейду; аннуитетный платёж.

Между шагами можно сделать настраиваемую задержку (`PIPELINE_STEP_DELAY_SECONDS`, по умолчанию 1–2 с), чтобы на демо было видно, как статус меняется в реальном времени.

После решения:
- клиент: `accept_offer` → `OFFER_ACCEPTED` → `sign` (имитация подписи, подтверждение в интерфейсе; можно сгенерировать «документ» — договор в PDF или HTML по шаблону) → `SIGNING` → автоматически `ISSUED` (имитация зачисления, запись события с суммой);
- клиент: `decline_offer` → `CLIENT_DECLINED`;
- клиент в `NEEDS_INFO`: `provide_info` (дополнить поля / загрузить документ) → снова `SUBMITTED` → пайплайн заново;
- сотрудник в `MANUAL_REVIEW`: `approve` (опционально с изменёнными условиями) / `counter_offer` / `request_info` / `reject` — с обязательным комментарием.

## API (префикс `/api/v1`)

Минимальный набор (уточни и дополни, если нужно):

**Auth**
- `POST /auth/login` → JWT
- `GET /auth/me`

**Справочники**
- `GET /products` — продукты с понятным описанием
- `POST /products/recommend` — подбор продукта по ответам клиента (цель, сумма, срок, как быстро нужны деньги) → упорядоченный список с объяснением «почему подходит». Простая rule-based логика из конфига.
- `GET /dictionaries/purposes` — цели финансирования

**Клиент**
- `GET /company` — моя компания
- `GET /applications` — мои заявки
- `POST /applications` — создать черновик
- `GET /applications/{id}`
- `PATCH /applications/{id}` — редактировать черновик
- `POST /applications/{id}/actions/{action}` — единая точка для действий (`submit`, `cancel`, `provide_info`, `accept_offer`, `decline_offer`, `sign`)
- `POST /applications/{id}/documents` / `GET /applications/{id}/documents`
- `GET /calculator?product=&amount=&term=` — предварительный расчёт платежа (для клиента до подачи)

**Сотрудник** (`/backoffice/...`)
- `GET /backoffice/applications` — очередь с фильтрами (статус, продукт, грейд) и пагинацией
- `GET /backoffice/applications/{id}` — полная карточка: анкета, данные компании, результаты проверок, скоринг с вкладом факторов, история
- `POST /backoffice/applications/{id}/actions/{action}` — `approve`, `counter_offer`, `request_info`, `reject`
- `GET /backoffice/stats` — простые метрики: заявок по статусам, доля автоодобрений, среднее время обработки

**Лента подсказок и новостей** (организаторы просят на демо показать персонализацию)
- `GET /feed` — персональная лента для клиента: подборка из `seed/feed_items.json` по отрасли (ОКВЭД), типу компании, статусу текущей заявки и продукту. Каждый элемент: заголовок, текст, тег, почему показан (`reason`). Логика отбора — правила в `config/feed.yaml`.

**Служебное**
- `GET /health` (liveness), `GET /ready` (readiness: проверка БД и mock-external)

Требования к API:
- Единый формат ошибок: `{ "error": { "code", "message", "details" } }`, сообщения на русском, понятные клиенту.
- Валидация всех входных данных через Pydantic.
- Пагинация в списках.
- Swagger UI на `/docs`; экспортируй схему в `docs/openapi.json`.
- CORS настраивается через env (для будущего фронта на `http://localhost:5173`).

## Сервис `mock-external`

Отдельный контейнер, имитирующий внешние системы:
- `GET /egrul/{inn}` — ответ в упрощённом, но правдоподобном формате выписки;
- `GET /bki/report?inn=` — упрощённый кредитный отчёт.

Данные детерминированы и берутся из `seed/external_mocks.json` по ИНН. Для неизвестного ИНН — сгенерированный правдоподобный ответ (детерминированно от ИНН). Поддержи «режимы сбоя» для демо отказоустойчивости: например, специальный ИНН, на котором БКИ отвечает таймаутом или 500.

## Синтетические данные (seed) — заглушки до датасета участника 3

Минимум:
- **сотрудник банка**: `employee` / `employee123`;
- **клиенты** (каждый — своя компания и свой сценарий):
  - `client_good` — сильный заёмщик → автоодобрение как запрошено;
  - `client_medium` — высокая нагрузка → встречное предложение;
  - `client_border` — пограничный грейд → ручное рассмотрение;
  - `client_bad` — просрочки / ликвидация → отказ;
  - `client_info` — неполные данные → запрос уточнений;
  - `client_timeout` — ИНН, на котором БКИ «падает» → ручное рассмотрение;
- пароли — `<логин>123`; все учётки перечисли в README;
- по 10–15 элементов ленты подсказок для разных отраслей и статусов;
- несколько уже существующих заявок в разных статусах, чтобы очередь сотрудника не была пустой.

## Безопасность и надёжность (enterprise-подход)

- Проверка прав на каждом эндпоинте: клиент видит только свою компанию, бэкофис — только `employee`.
- Хеширование паролей, срок жизни токенов, секрет из env.
- Ограничения на загрузку файлов (тип, размер), безопасные имена файлов.
- Rate limit на `/auth/login` (простой, in-memory допустим — укажи в assumptions).
- Request id в логах и заголовке ответа, логирование всех смен статусов.
- Персональные данные не пишутся в логи.
- Healthchecks в Docker, `restart: unless-stopped`.
- Идемпотентность действий: повторная отправка того же действия не ломает состояние.
- Stateless-бэкенд (можно масштабировать горизонтально) — отметь в architecture.md, что нужно для этого в проде (очередь вместо фоновых задач, объектное хранилище для файлов и т. п.).

## Тесты

- Юнит-тесты: машина состояний (все допустимые и несколько недопустимых переходов), скоринг (каждый фактор), кредитное решение, аннуитетный платёж, валидация ИНН.
- Интеграционные / e2e (через API, с поднятой тестовой БД): для каждого seed-клиента — полный сценарий от создания заявки до финального статуса; сценарий `NEEDS_INFO → provide_info → OFFER_SENT`; ручное рассмотрение сотрудником; доступ клиента к чужой заявке → 403/404.
- Команда запуска тестов в контейнере описана в README.
- Опиши эти же сценарии по-человечески в `docs/test-scenarios.md` (шаги, логин, ожидаемый результат) — по ним жюри будет проверять вручную.

- `docs/api.md`: обзор API и типовой сценарий запросов.
- `docs/requests/`: Postman-коллекция (и/или `.http`-файлы) для сквозного сценария клиента и сотрудника.
- `docs/assumptions.md`: все допущения и упрощения.
- `THIRD_PARTY_NOTICES.md`: все сторонние библиотеки с лицензиями, используемые образы Docker, и явный список **смоделированных интеграций** (БКИ, ЕГРЮЛ/ЕГРИП, подписание, выдача средств).

## Порядок работы

Работай этапами. После каждого этапа: запусти тесты и `docker compose up --build`, убедись, что всё работает, сделай отдельный git-коммит с понятным сообщением.

1. Каркас: структура, Docker Compose, `db` + `backend` + `mock-external`, `/health`, lock-файлы, `.env.example`.
2. Модели, миграции, seed-загрузчик, авторизация и роли.
3. Машина состояний + `ApplicationEvent` + `available_actions` + тексты из `labels.yaml`.
4. Клиентские эндпоинты, продукты, подбор продукта, калькулятор.
5. `mock-external` + клиенты интеграций с ретраями и таймаутами.
6. Скоринг, кредитное решение, расчёт предложения, пайплайн.
7. Бэкофис-эндпоинты и статистика.
8. Документы (загрузка) и имитация подписания и выдачи.
9. Лента подсказок `/feed`.
10. Тесты (юнит + e2e) — доведи до зелёного состояния.
11. Документация, экспорт `openapi.json`, коллекция запросов, THIRD_PARTY_NOTICES.
12. Финальная проверка: удали volume, `docker compose up --build` с нуля, пройди сценарии из `docs/test-scenarios.md` запросами, исправь всё, что сломалось.

Код и комментарии — читаемые для джуниор-разработчиков: простые имена, без лишней магии и избыточных абстракций. Где делаешь заглушку под данные коллег — явный `TODO(участник N)`.

В конце выведи:
- как запустить;
- список тестовых учёток и что каждая демонстрирует;
- какие конфиги нужно будет заменить, когда участники 2 и 3 пришлют данные;
- список того, что не успел или упростил.
